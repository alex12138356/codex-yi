# 回传日志设计指南

## 一、为什么需要回传日志

在多智能体协作系统中，一个普遍存在的结构性问题是：

**各执行单元互相不知道对方的存在与进展，而只有一个调度者掌握全局。**

如果每个执行单元只埋头完成自己的任务，调度者就会陷入"需要亲自询问才能知道进度"的状态。这在以下场景中会迅速失控：

- 执行单元数量超过 3 个
- 执行单元有异步依赖关系（一个单元的产出是另一个单元的输入）
- 调度者需要在不知道细节的情况下做方向性判断

回传日志（Return Log）正是为了解决这个结构性矛盾而设计的一种通信协议。

---

## 二、回传日志在系统中的作用

回传日志不是汇报制度，而是一种**认知对齐机制**。它在系统中承担四个核心角色：

| 角色 | 说明 |
|------|------|
| **状态同步信号** | 让调度者在不主动询问的情况下，知道每条线的实时状态 |
| **决策触发信号** | 当一条线完成阶段性工作或遇到阻塞时，触发中枢的判断流程 |
| **上下文压缩接口** | 将执行线中发生的大量对话和操作，压缩为调度者可读的一条记录 |
| **跨线知识传递** | 线 A 的发现可能对线 B 有价值，回传日志是传递的起点 |

一个健康的系统，调度者应该可以**只读回传日志，就知道所有线的进展**，而不需要进入每一条线看原始对话。

---

## 三、什么该回传

回传的判断标准只有一个：**这条信息，调度者不知道的话，他做判断会出错。**

具体来说，以下五种情况必须回传：

### 1. 阶段性结果
- 调研完成，有了结论
- 原型跑通，验证了一个假设
- 文档写完了、项目上线了
- 没有预期成果的探索也回传——"这条路走不通"本身就是有价值的信息

### 2. 方向性决策
- 决定了一个技术方案
- 拒绝了某个方向并说明了原因
- 需要多个执行线配合才能推进的事

### 3. 阻塞状态
- 遇到硬 blocker，无法自行推进
- 需要调度者做方向性判断
- 等待外部资源/信息，且预计会拖慢进度

### 4. 初始化确认
- 新执行单元启动后，确认已到位、已理解任务
- 进度归零也是状态，比"无声"更有价值

### 5. 完成信号
- 用户明确要求的任务已完成
- 可以进入下一阶段的确认

---

## 四、什么不该回传

回传日志需要保持"可扫读"的密度。以下是明确不应该回传的内容：

| 类别 | 例子 | 处理方式 |
|------|------|----------|
| 操作细节 | "我修改了第 37 行的变量名" | 不需要传递 |
| 正在做的事 | "我还在分析 A 文件" | 在没有结果前不需要报 |
| 对话原文 | 完整的对话记录 | 存储在项目文件里，回传只给摘要 |
| 情绪状态 | "这个任务好难我好累" | 不是结构性问题就不需要回传 |
| 无意义的确认 | "好的我收到了" | 除非是初始化确认，否则默认收到即可 |

**一个实用的过滤规则**：如果你删掉这条回传，调度者的判断会不会出错？如果不会，就不要写。

## 五、格式怎么写

回传日志的格式设计原则是：**调度者只看一次，就能判断需不需要深入**。

### 推荐格式

每条回传日志包含三个层级的信息：

```
[执行线标识] 行为阶段 — 一句话摘要

详情：路径/到/项目文件.md

要素：
- 做了什么
- 结论是什么
- 下一步是什么
- 需要调度者做什么
```

### 示例

```
[内容产出线] 调研完成 — 确定了第一期选题方向

详情：/Users/alice/Documents/content/选题池.md

要素：
- 分析了 20 个同类账号的高赞内容
- 结论：实操教程类内容互动率最高
- 下一步：写第一篇大纲
- 需要调度者：不需要，按计划推进
```

### 格式要点

1. **第一行必须是一句话摘要** — 调度者扫读这一行就能决定要不要深入
2. **详情用文件路径而非内嵌** — 保持回传日志本身轻量，细节存在项目文件里
3. **要素只有四类** — 做了什么、结论、下一步、需要调度者做什么
4. **不写废话** — 格式是辅助扫读的，不是模板填空

## 六、回传频率怎么定

回传频率不是"每隔 X 分钟/小时回传一次"，而是**按事件触发**。

| 触发条件 | 频率描述 |
|----------|----------|
| 阶段完成 | 完成一个可定义的阶段性工作后立即回传 |
| 遇到 blocker | 以 blocker 事件为单位，一次一报 |
| 做出决定 | 做出重要决策后立即回传 |
| 用户明确要求 | 用户说"做完了回传"，完成时必须回传 |

### 常见误区

- **误区：频繁回传 = 更负责** → 高频无意义的回传只会增加调度者的认知负担
- **误区：做完一个步骤就回传** → 步骤之间没有独立的判断价值，等阶段完成再报
- **误区：进度慢就不回传** → 进度慢本身不是不回传的理由，如果慢是因为 blocker，就触发 blocker 回传；如果慢是因为正常推进，等阶段完成再报

### 一个简单的频率判断流程

```
当前进度 → 是不是一个完整的阶段？
  ├─ 是 → 回传
  └─ 不是
       └─ 有没有 blocker？
            ├─ 有 → 回传
            └─ 没有 → 继续推进，下一次再判断
```

## 七、回传日志的演进

随着系统运行，回传日志本身会经历几个阶段：

| 阶段 | 特征 | 需要关注的事 |
|------|------|-------------|
| **启动期** | 回传密集，各线在建立节奏 | 关注是不是每条线都在回传，防止沉默线 |
| **稳定期** | 回传节奏成型，格式一致 | 关注回传质量而非频率，防止格式退化 |
| **成熟期** | 调度者扫读回传即可做全局判断 | 关注回传传递效率，考虑引入结构化的回传索引 |

在一个长期运行的系统中，回传日志会从"基础设施"变成"系统记忆"。即使在系统停止运行后，回传日志本身也是最有价值的文档资产之一——它记录了每条线的决策路径和关键节点。

---

## 八、从设计到落地

回传日志的核心价值不在于格式多完美，而在于**它真的被读、被用**。

三个检查清单：

1. **调度者能否只读回传日志就知道全局？** — 如果不能，说明回传密度不够
2. **调度者是否需要翻大量原文才知道细节？** — 如果是，说明回传摘要质量不够
3. **调度者是否需要主动询问"那个任务怎么样了"？** — 如果是，说明回传机制还没跑通

设计一个好用的回传日志机制，本质上是在问一句话：

> **"我怎么让调度者不需要亲自走进每条线，就能安全地做全局判断？"**
>
> 能回答这个问题，回传日志就起作用了。
