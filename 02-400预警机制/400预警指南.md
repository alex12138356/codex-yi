
# 400 预警与主动写盘机制

> **一份关于 Codex 对话上限、主动保存、以及何时该开新线的方案指南**
> 方法论导向 · 不涉及具体用户信息

---

## 一、什么是 400 截断

### 1.1 定义

"400 截断"不是时间限制，是文字量限制。每个 Codex 对话都有最大 token 容量——到上限后，系统会自动截断历史记录。截断后，这个对话里的一切都停了：上下文没了，记忆没了，继续聊下去的是"新的 AI"，它看不到之前的任何内容。

这不是 bug，这是每个深层对话都会遇到的天花板。

### 1.2 核心影响

| 维度 | 影响 |
|------|------|
| **上下文丢失** | 所有之前的讨论、决策、判断依据，一次性消失 |
| **状态重置** | AI 回到初始状态，不知道你是谁、聊过什么 |
| **信任断裂** | 用户与 AI 之间建立的工作默契被硬切断 |
| **投入归零** | 长对话中积累的隐性知识（语气、判断偏好、信任）全部丢掉 |

### 1.3 一个常见的误区

很多人以为"400 限制可以靠压缩问题、减少字数来规避"。实际上，400 限制由**对话双方的总文字量**决定——你少说两句，不代表 AI 回答也会变短。真正有效的不是省字数，而是**主动管理对话生命周期**。

## 二、什么时候该预警

预警不是靠"感觉对话好像长了"。预警需要可操作的信号。

### 2.1 宏观信号（对话年龄维度）

- **持续 3-5 天的高频使用**：每天深入对话，3-5 天基本接近上限
- **30-50 轮以上的深层讨论**：每轮包含长思考、长回答，比短轮对话更快消耗容量
- **内容产出丰富的对话**：如果是写代码、写文档、长文分析，每轮消耗量大幅增加
- **一次对话解决多个话题**：一个对话里聊了 A → B → C → D 四个不相关话题，每个话题都要花 token 重新建立上下文

### 2.2 微观信号（对话体验维度）

- AI 开始出现"记不清前面说了什么"的迹象
- AI 的回答变短、不愿意深入展开
- AI 建议"要不要把这个总结一下写到文件"
- 你自己也开始觉得"前面聊的内容好像远了"

### 2.3 硬性触发条件（遇到即预警）

满足以下条件之一，就该执行写盘操作：

1. **完成了任何阶段性成果**（调研完成、方案确定、代码跑通）
2. **做出了不可逆的判断**（决定投钱、决定不做某件事）
3. **遇到了需要切换话题的转折点**（一个事聊完了，要聊下一个）
4. **对话状态发生变化**（用户情绪有重要波动、认知有结构性更新）
5. **AI 主动提及"对话快超限了"**

### 2.4 预警节奏建议

| 阶段 | 操作 | 时机 |
|------|------|------|
| 初期 | 每完成一个小里程碑写盘一次 | 持续记录 |
| 中后期 | 每完成一个话题就写盘 | 减少单次写工作量 |
| 接近上限 | 每次关键输出后立即写盘 | 防止突然截断 |

> **核心原则**：不等"对话已经满了"再写。在感觉"可能快满了"的时候就开始写。这个动作不需要用户开口说"记下来"。

## 三、怎么主动写盘

### 3.1 核心思路

主动写盘 = **把对话中的关键信息写到磁盘文件，确保截断后新对话能无缝接上。**

不是"把整个对话复制到文件里"。是有选择的、结构化的提炼。

### 3.2 SESSION_LOG 机制（标准做法）

每个对话维护一个 `SESSION_LOG.md`，记录对话的核心状态。结构如下：

```markdown
# SESSION_LOG

> 共享知识库（全局上下文）见：[路径/共享知识库.md]
> 完整对话历史（可选）见：[路径/对话日志.md]

## [日期] -- [本轮主要事件]

### 关键进展
- 完成了什么
- 发现了什么
- 产出了什么

### 重要决策
- 决定了什么
- 为什么决定（一句话理由）

### 未完成待办
- [ ] 下一步要做什么
- [ ] 需要谁配合

### 用户状态
- 用户当前的判断/情绪/优先级（只记可被下一轮复用的信息）
```

### 3.3 四种写盘场景

#### 场景 A：即时写盘

用户说了一句重要的话 / 你做了一次重要产出，当场写进文件。

> 不等待。不等他说"记下来"。不等对话结束。现在写。

**例子**：用户说"我应该试试这个方向" → 打开 `SESSION_LOG.md` → 更新关键进展。

#### 场景 B：阶段总结写盘

完成一个阶段后，整理该阶段的所有关键信息写盘。

**特点**：综合性的、聚合的。把碎片串成逻辑链。

#### 场景 C：预警写盘

对话接近上限时，紧急写盘。优先级最高。

**特点**：只记最核心的信息。"如果下一轮对话只能读两句话，该读什么？"

#### 场景 D：项目沉淀写盘

不只在 `SESSION_LOG.md` 写。重要项目应该有自己的盘记录文件。

> 项目盘记录：`/项目路径/records.md`
> 项目细节不在共享知识库中全文存储，用一行路径引用代替。

### 3.4 写盘标准对照表

| 信息类型 | 写入位置 | 写入时机 | 详细程度 |
|----------|----------|----------|----------|
| 当前进展 | SESSION_LOG | 即时/阶段性 | 中等（标题+关键结果） |
| 重要决策 + 理由 | SESSION_LOG | 决策做出时 | 简短（决策+一句话理由） |
| 用户认知更新 | 共享知识库 | 发现时 | 结构化（按分类写） |
| 项目细节/结论 | 项目文件 | 完成时 | 完整（可被独立阅读） |
| 待办事项 | SESSION_LOG | 随时 | 清单格式 |
| 全局上下文更新 | 共享知识库 | 阶段性 | 精炼（一行引用+路径） |

### 3.5 写盘质量标准

一条合格写盘记录应该满足：

- ✅ 下一轮对话能理解"上轮发生了什么"
- ✅ 下一轮对话知道"下一步要做什么"
- ✅ 关键决策有理由，不是只有结论
- ✅ 文件路径可访问
- ❌ 不要事无巨细，记日志不是记流水账

## 四、开新线的判断标准

### 4.1 什么时候需要开新对话

不是所有"对话快满了"都要开新线。以下情况应该开新线：

| 条件 | 应该开新线 | 不应该开新线 |
|------|-----------|-------------|
| 话题完全切换 | ✅ 聊完 A 要聊 B，各走各的 | ❌ 还在深度讨论同一个话题 |
| 需要保持独立状态 | ✅ 两个项目并行推进 | ❌ 单一调研还在进行中 |
| 角色不同 | ✅ 调研角色 vs 执行角色 | ❌ 相同角色的延续 |
| 需要不同上下文 | ✅ 股票盘数据 vs 知识库认知 | ❌ 共享同一组上下文 |
| 对话已接近上限 + 还要继续 | ✅ 先写盘再开新线 | ❌ 还有大量容量继续聊 |

### 4.2 开新线的标准流程

```
1. 确认当前对话的状态
   → 读 SESSION_LOG
   → 确认"当前进度"和"待完成"

2. 判断是否该开新线
   → 用 §4.1 的标准对照
   → 如果判断"是"，往下走

3. 写盘（开新线前必须完成）
   → 更新 SESSION_LOG（当前对话的完整状态）
   → 确保新线需要的上下文都在磁盘上

4. 打包新线的启动指令
   → 包含：新线的角色职责、读哪些文件、工作方式、回传要求

5. 开新对话
   → 把启动指令粘贴到新对话的任务描述
   → 确保新对话第一时间读共享知识库
```

### 4.3 一个常用的判断框架

"该不该开新线"可以这样想：

> **如果今天对话突然被截断了，丢失的内容里——**
> - 有 80% 以上的信息我已经写到文件里了 → 不需要新线，继续就好了
> - 有 50% 以上的信息还没写盘，而且写出来会很长 → 先写盘，考虑是否该开新线
> - 是一个全新的话题，跟当前对话没有上下文关联 → 应该开新线

### 4.4 不建议开新线的情况

- 当前对话还在有效工作，容量充足
- 话题延续性强，切断了反而丢失连贯性
- 用户没有明确说明需要分开管理

## 五、系统层面的设计思考

### 5.1 400 主动防御的本质

400 预警不是"应急方案"，它是一套**主动管理系统**。它的核心设计逻辑是：

> **对话是无状态的会话，文件是持久的记忆。**

你不应该在对话里积累一切。对话是处理过程，文件是存储介质。处理好一个节点就写盘，下一个节点接着走，对话本身只是管道。

### 5.2 与多线系统的关系

400 预警不是独立存在的。它是**多线协作系统**（如"Codex 壹"）的底层基础设施之一：

| 系统组件 | 作用 |
|----------|------|
| 共享知识库 | 全局上下文，所有对话共享 |
| SESSION_LOG | 每个对话的状态日志 |
| 回传日志 | 执行线→中枢的状态同步 |
| 400 预警 | 防止任何一个对话的信息丢失 |

一个对话被截断并不可怕——只要写盘到位，新对话读一下文件就可以无缝接上。

### 5.3 建议的最小文件架构

```
项目目录/
├── SESSION_LOG.md         # 当前对话的状态日志（每个对话一个）
├── records.md              # 项目级的完整盘记录
└── 共享知识库.md          # 全局上下文（所有对话共用，放桌面）
```

如果一个对话有这 3 层文件保障，它被截断后的影响是可控的。

### 5.4 进阶：自动化的可能性

以上操作目前都是手动完成的。理论上可以做到：

- 写一个 CLI 工具，一键生成 SESSION_LOG 摘要
- 用 Codex SKILL 自动化写盘流程（检测到关键信息自动写盘）
- 在对话启动时自动注入"SESSION_LOG 读取 + 工作方式说明"

但这已经不是"400 预警机制"的核心了。核心是：**你能不能养成主动写盘的习惯。工具可以优化体验，但不能替代判断。**

## 附录 A：快速检查清单

**写盘前问自己**：
- [ ] 当前的关键进展写了吗？
- [ ] 做了重要的决策吗？理由写了吗？
- [ ] 用户有什么新的认知/判断？写了没？
- [ ] 下一步要做什么，写清楚了吗？
- [ ] 如果这个对话现在截断，新来的能直接接上吗？

**开新线前问自己**：
- [ ] 这是同一个话题还是新话题？
- [ ] 当前对话的 SESSION_LOG 更新了吗？
- [ ] 新线需要的上下文在磁盘上吗？
- [ ] 新线的职责和工作方式写清楚了吗？
- [ ] 开新线后，老线还需要保留吗？

## 附录 B：常见问题

**Q: 对话被截断后，SESSION_LOG 还能读到吗？**
> 能。SESSION_LOG 是磁盘文件，不依赖对话存活。新对话第一条指令就是读它。

**Q: 如果一次写了很长的 SESSION_LOG，会不会占太多 token？**
> 控制 SESSION_LOG 篇幅是合理的。写最关键的，不要写流水账。超过 5 行才能说清楚的东西走项目文件引用。

**Q: 共享知识库和 SESSION_LOG 有什么区别？**
> 共享知识库 = 关于"用户是谁"的全局上下文（不随时间快速变化）。SESSION_LOG = 关于"这个对话正在进行什么"的会话上下文（每次对话不同）。

**Q: 开了新线之后，老线剩下的容量还能用吗？**
> 可以。老线的剩余容量可以在需要回顾历史、做跨线整合时使用。但主要工作已经迁移到新线了。
