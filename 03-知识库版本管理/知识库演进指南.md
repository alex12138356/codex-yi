# 知识库演进指南

## 从 v1 到 v3：一个共享知识库的版本进化史

### 起源：为什么要造一个共享知识库？

故事的起点是一个很朴素的问题：多个智能体对话同时运行，每个对话都在独立学东西，但彼此之间完全隔离。每个新对话启动时，都要从零开始重新交代一遍同样的背景信息。

这不仅效率低，而且容易出错。A 对话刚跟用户确认了某个方向，B 对话启动时完全不知道，又用旧前提做判断。

**第一版解决方案：写一个文件，每次启动先读。**

---

## v1：全写进去（大一统阶段）

**设计思路**

把所有需要知道的信息全部写进同一个文件：
- 用户背景（身份、位置、个性、信条）
- 系统机制（对话生命周期、限制、解决方案）
- 所有项目的全部细节（背景、策略、结论、当前状态）
- 工作方式偏好

**为什么这么设计**

当时的直觉是"一次读完，什么都知道了"。不要分文件，不要跳转，不要额外读取。一个文件通杀所有上下文需求。

这是最直觉的写法——把所有信息 dump 到一个地方，简单直接。对于文件本身来说，它是"完整"的；对于阅读者来说，读完就能了解全局。

**遇到的问题**

随着项目增多和多条并行线运作，文件越长越痛苦：
- 每个新对话都要读越来越长的文件，启动变慢
- 项目细节不断变化，但知识库来不及同步，内容总是滞后
- 读完才知道"哦，这个项目的细节已经过期了"
- 一个项目改策略，要改知识库里的一大段正文

**核心矛盾**：知识库应该提供稳定的上下文，但项目细节是高速变化的信息。把两者放在同一个层级的写法，让知识库变成了一个"需要频繁维护但永远追不上变化"的负担。

---

## v2：路径引用（结构化阶段）

**设计思路**

把知识库拆成两层：
1. **知识库本体**：只保留必须知道的信息
2. **项目文件**：每个项目的细节独立存储在各自目录下

知识库本体里不再写项目细节，而是写一行文件路径引用。需要细节的对话，按路径去读对应文件。

**为什么这么设计**

识别出一个关键区别：有些信息是"一次性知道就够了"的，有些信息是"需要反复查"的。

- 用户是谁、红线是什么、系统机制——一次性知道就够了，每次启动都读一遍
- 项目调研细节、持仓情况、策略方案——只有需要深挖时才需要读

基于这个区别：
- 知识库本体 = 常驻上下文，每次启动必读
- 项目文件 = 按需读取，只在需要时加载

这样知识库变短了，每个对话启动时不需要读完整本书。同时项目文件保持独立，更新项目不影响知识库。

**引入的配套规范**

v2 不只是一个文件结构的改动，还引入了三个配套机制：
1. **项目文件引用规范**：什么写知识库、什么走文件路径引用，有明确的分界线
2. **新对话启动规范**：任务描述里直接打包工作方式
3. **回传机制**：各线完成重要阶段后，统一写到中央日志，让中枢不用人肉传话

**还存在的问题**

v2 解决了"信息膨胀"和"同步滞后"，但引入了一个新问题：知识的粒度没有区分。

知识库里仍然包含多种粒度的信息，从一句话的事到一段长认知段落。这些信息对每个对话的"必读程度"完全不同。有的对话每次启动都需要，有的对话只在特定场景下有用。

---

## v3：按粒度分层（成熟阶段）

**设计思路**

把知识库内的信息按访问频率和时效性分为三层：

| 层级 | 内容特征 | 访问策略 |
|------|---------|---------|
| L1：核心上下文 | 稳定不变，每次启动必须知道 | **每次必读** |
| L2：操作参考 | 偶尔更新，只有在执行时才需要 | **启动时读，执行时参考** |
| L3：历史沉淀 | 过去判断的记录，当前行动不需要 | **标记为"跳过"，只在需要时回顾** |

在文件结构上的体现：
- L1：用户身份 + 系统机制 + 对话架构（每次必读）
- L2：项目一览 + 启动规范 + 文件引用规范（执行时参考）
- L3：使用方式 + 历史 + 过往认知沉淀（附注释"新对话跳过"）

**为什么这么设计**

经过 v1 和 v2 的实践，意识到一个问题：不是所有知识对每个对话都有同等价值。

- 新启动的对话只需要 L1。知道用户是谁、系统怎么运行、当前有哪些线在跑，就能接上工作
- 要执行任务的对话需要 L2。知道项目文件在哪、回传怎么写、工作规范是什么
- 只有需要做判断的对话才需要 L3。过往认知沉淀——这些是用户本人回头看的，新对话根本不需要知道

L3 加了一句明确的注释："新对话启动时跳过这节。" 这一行注释本身就是 v3 的核心设计理念：**减少隐性成本。**

**隐性成本的发现**：即使文件变短了，每个新对话启动时仍然要读一遍全文，才能确定哪些是"与我相关"的信息。v3 把"相关性的判断权"从读者转移到作者。在文件中明确标注哪些是必读、哪些是参考、哪些可以跳过，让每个对话可以在 2-3 分钟内完成启动。

## 核心经验总结：别人怎么抄这个作业

### 什么时候该从 v1 升级到 v2

**信号**：
- 知识库文件越来越长，每次编辑都像在翻一本小说
- 项目信息频繁变化，你发现自己经常在知识库里改细节
- 新成员/新对话启动时，花很多时间在帮你理解上下文上

**动作**：
1. 识别出哪些信息是稳定的、哪些是变化的
2. 稳定的留在知识库里，变化的用文件路径引用
3. 为每个变化的信息块建立独立文件
4. 引入配套规范（启动规范 + 回传机制）

### 什么时候该从 v2 升级到 v3

**信号**：
- 知识库内还有长段内容，但其实不是每次都用到
- 新对话启动时虽然读了全文，但仍然不清楚哪些应该重点关注
- 附录式的沉淀越来越多，你有冲动想删掉但又觉得有价值

**动作**：
1. 给知识库里的每条信息标注必读/参考/跳过
2. 按粒度重组章节顺序：最核心的放最前面
3. 为低频信息加明确的跳过指示（注释或标签）
4. 考虑为 L3 层级的内容建立独立的认知日志，知识库里只保留链接

### 这套思路的通用性

这个三阶段演进模式可以套用到任何多人/多智能体共享上下文的场景：

| 场景 | 核心迁移 |
|------|---------|
| 团队 Wiki | 全写在一个页面 → 目录+子页面 → 按角色/场景标记阅读优先级 |
| 开发者指南 | 全文写全部 API 用法 → 概述+各接口文档链接 → 标注核心/常用/高级 |
| 项目复盘 | 所有讨论过程写一个文档 → 结论+文件链接 → 标注必读/选读过程 |
| 学习笔记 | 所有笔记写一个文件 → 按主题拆分 → 标注核心概念/需掌握/拓展了解 |

**底层的洞察是同一个**：信息的价值取决于读取它的场景。不分场景地堆砌信息，价值会稀释。分场景分层级，价值才会放大。

---

## 附：这个模式的几个关键约束

1. **分层不是越细越好。** 三层就够了。分太多层会让查知识本身成为负担。
2. **L1 要极度克制。** 只放绝对必需的信息。每多一行，所有新对话启动时都要多花一份时间。
3. **"跳过"标记要有纪律。** 标注了跳过的内容，真的不应该被新对话读取。如果有对话频繁需要回看某段跳过的内容，说明它应该升到 L2。
4. **v1→v2 是最疼的一次跳跃。** 因为需要拆文件和建引用规范。v2→v3 相对轻，主要是结构调整和注释优化。
5. **回传机制是配套件，不是可选项。** 没有回传机制的多线系统，知识库早晚会再次膨胀——因为中枢不知道各线进度，只能把所有可能性都写进知识库。
6. **这个模式的终点不是一个完美的文件，而是一个稳定的启动体验。** 衡量指标很简单：新对话能在 2 分钟内接上内容，知道该做什么、去哪查。
