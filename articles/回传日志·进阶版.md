# 回传日志·进阶版

## 适用人群

已有多条执行线在并行运行，调度者需要频繁确认各线状态，希望建立结构化的回传制度来替代低效的主动询问。

---

## 核心理念

**回传日志不是汇报制度，而是认知对齐机制。**

它的核心目标只有一个：**让调度者不需要走进每条线，就能安全地做全局判断。** 调度者只读回传日志，就应该知道所有线的进展——不需要进入每一条线看原始对话。

---

## 四种必须回传的情况

| 触发条件 | 定义 | 例子 |
|----------|------|------|
| **阶段性结果** | 完成了可独立定义的阶段 | 调研完成、原型跑通、文档定稿 |
| **方向性决策** | 做出了影响后续方向的决定 | 否决某方案、确定技术栈 |
| **阻塞状态** | 无法自行推进 | 遇到 blocker、需要方向性判断 |
| **初始化确认** | 新线启动后的到位确认 | "已到位，开始干活" |

每种情况都只需要一句话摘要 + 文件路径。不需要对话原文。

---

## 明确不报的内容

| 类别 | 例子 | 原因 |
|------|------|------|
| 操作细节 | "我改了第 37 行的变量名" | 不影响判断 |
| 无结果的状态 | "我还在分析 A 文件" | 没有结论就不创造价值 |
| 对话原文 | 完整的对话记录 | 回传是摘要，不是全文 |
| 情绪状态 | "这个任务好难我好累" | 不是结构性问题 |
| 无意义的确认 | "好的我收到了" | 默认收到即可 |

**实用过滤规则**：如果你删掉这条回传，调度者的判断会不会出错？如果不会，就不要写。

---

## 标准格式：三级信息

每条回传日志包含三个层级：

```

[线标识] 阶段 — 一句话摘要

详情：/path/to/项目文件.md

要素：
- 做了什么
- 结论是什么
- 下一步是什么
- 需要调度者做什么
```

### 格式要点

1. **第一行必须是一句话摘要** — 调度者扫读这一行就能决定是否深入
2. **详情用文件路径而非内嵌** — 保持回传日志轻量，细节存在项目文件里
3. **要素只有四类** — 做了什么、结论、下一步、需要调度者做什么
4. **不写废话** — 格式是辅助扫读的，不是模板填空

## 频率控制：事件触发，不是定时触发

| 触发条件 | 频率描述 |
|----------|----------|
| 阶段完成 | 完成一个可定义的阶段性工作后立即回传 |
| 遇到 blocker | 以 blocker 事件为单位，一次一报 |
| 做出决定 | 做出重要决策后立即回传 |
| 用户明确要求 | 说"做完了回传"，完成时必须回传 |

### 常见误区

- 误区：频繁回传 = 更负责 → 高频无意义的回传只会增加调度者的认知负担
- 误区：做完一个步骤就回传 → 等阶段完成再报
- 误区：进度慢就不回传 → 进度慢本身不是不回传的理由，如果慢是因为 blocker，就触发 blocker 回传

### 频率判断流程

```
当前进度 → 是不是一个完整的阶段？
├─ 是 → 回传
└─ 不是
    └─ 有没有 blocker？
        ├─ 有 → 回传
        └─ 没有 → 继续推进，下次再判断
```

## 回传日志的演进阶段

| 阶段 | 特征 | 关注点 |
|------|------|--------|
| **启动期** | 回传密集，各线在建立节奏 | 是否每条线都在回传，防止沉默线 |
| **稳定期** | 回传节奏成型，格式一致 | 回传质量而非频率，防止格式退化 |
| **成熟期** | 调度者扫读回传即可做全局判断 | 回传传递效率，考虑引入结构化索引 |

在一个长期运行的系统中，回传日志会从"基础设施"变成"系统记忆"。即使系统停止运行，回传日志本身也是最有价值的文档资产之一——它记录了每条线的决策路径和关键节点。

---

## 三个检查清单

1. **调度者能否只读回传日志就知道全局？** — 如果不能，说明回传密度不够
2. **调度者是否需要翻大量原文才知道细节？** — 如果是，说明回传摘要质量不够
3. **调度者是否需要主动询问"那个任务怎么样了"？** — 如果是，说明回传机制还没跑通

设计一个好用的回传日志机制，本质上是在问一句话：

> **"我怎么让调度者不需要亲自走进每条线，就能安全地做全局判断？"**

能回答这个问题，回传日志就起作用了。
