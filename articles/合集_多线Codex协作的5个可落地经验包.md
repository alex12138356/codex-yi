# 合集：用多线 Codex 协作系统跑出 5 个可落地的经验包

> 当你同时管理多条并行线，最大的成本不是做事的精力——是让人脑记住每条线在干什么。
>
> 发布时间：2026-07-26 | 所属系列：多线协作实战

---

## 为什么需要一套"经验包"

多线协作最隐蔽的成本，不是对话长度限制——那是个技术问题，有明确的工程解法。

真正隐蔽的成本是**判断成本**：什么时候该开新线、什么时候该合并、什么时候该停。什么时候该回传什么信息。一份回传怎么写才能让调度者扫一眼就知道全局。

这些不是技术问题，是**决策框架问题**。如果你让每条线自己摸索怎么运转，成本不是线性的——每多一条线，混乱度翻倍。

下面这 5 个经验包来自同一个实战体系，每个解决一个结构性问题。你不需要一次全部用上，从最痛的开始，按需接入。

---

## 经验包 1：新对话启动规范

**解决什么问题**

开一条新线，需要交代的信息太多——背景、工作方式、回传规则、文件路径。每次都口头说一遍，第一效率低，第二总会漏掉关键项。漏了某条回传规则，中枢就不知道进度。漏了文件路径，新线就自己乱存。

**怎么用**

一份填空模板 + 一份任务描述 + 一份检查清单。开新线前把模板填好，把任务描述直接粘贴到新对话的输入框里。前置准备里包含中枢是谁、知识库路径、回传日志路径、已有线列表。任务描述里打包了四条工作规范（调研优先、关键信息写盘、重要阶段回传、不重复提问）。最后用检查清单确认新线已初始化。

**亮点设计**

模板里有一个"隐私规则"区块——这是为有对外产出需求的对话准备的，在任务描述阶段就注入过滤规则，避免产出内容泄露不该公开的信息。

## 经验包 2：400 预警机制

**解决什么问题**

对话长度到达上限时截断，所有上下文一次性丢失。这不是偶发事件——每个深度对话都会遇到这个天花板。而大多数人等到了截断那一刻才开始后悔。

**怎么用**

这套机制不靠"感觉"，靠可操作的信号。宏观信号（持续 3-5 天高频使用、30-50 轮深层讨论）、微观信号（AI 答非所问、回答变短）、硬性触发条件（有阶段性成果、做出不可逆判断、遇到转折点）。检测到信号就执行主动写盘，把关键状态写入磁盘文件 SESSION_LOG.md。

**亮点设计**

区分了四种写盘场景：即时写盘（不等用户说"记下来"）、阶段总结写盘（把碎片串成逻辑链）、预警写盘（只记两句话核心）、项目沉淀写盘（写入独立项目文件）。每种场景有不同的详细度和优先级。截断后新对话打开 SESSION_LOG 就能无缝接上——共享知识库告诉新对话"你是谁"，SESSION_LOG 告诉新对话"做到哪了"。

## 经验包 3：知识库版本管理

**解决什么问题**

共享知识库是系统的核心文件，但它容易膨胀——项目细节越来越多、附录越来越厚。每个新对话启动时都要读完整本书，启动成本越来越高。同时项目细节频繁变化，知识库里的内容总是滞后。

**怎么用**

三阶段演进路线：v1 把所有信息写进一个文件（直觉但不可持续）→ v2 拆出项目文件路径引用（把稳定信息和变化信息分层）→ v3 按粒度分层（L1 核心必读 / L2 操作参考 / L3 历史跳过）。每个阶段有自己的升级信号。

**亮点设计**

v3 的核心洞察："相关性的判断权从读者转移到作者。" 传统知识库让每个阅读者自己判断哪些信息相关。v3 的写法是在文件中明确标注：这是必读的、这是参考的、这是可以跳过的。标注本身比文件内容更像一个产品设计。

## 经验包 4：多线决策树

**解决什么问题**

多线系统最大的判断负担：什么时候该开新线？什么时候该合并？什么时候该停？各线之间怎么分工？没有决策框架之前，每个判断都是凭直觉，直觉在不同场景下不一致。

**怎么用**

一张四问决策表 + 五种线型定义 + 一套停线/合线流程。四问按顺序回答：是否与现有线重叠 → 现有线是否忙不过来 → 复杂度多高 → 拆分点是否清晰。答案组合直接映射到动作（归入现有线 / 开独立线 / 分裂子线 / 开并行线）。

**亮点设计**

五种线型（永久线、任务线、探索线、子线、并行线）各有明确的启动条件、管理方式和风险提示。比如探索线的核心约束是"设预算，预算耗尽时必须出结论"——防止调研变消遣。停线触发器中有一条很实："如果你对某条线说'留着以后可能有用'，它大概率已经该停了。"

## 经验包 5：回传日志设计

**解决什么问题**

各线埋头干活，调度者需要亲自询问才知道每条线的进度。当执行单元超过 3 个，这模式就崩了——调度者根本记不住每条线的最新状态。

**怎么用**

一份设计指南，回答四个核心问题：什么该回传（一条原则 + 五种必须回传的情况）、什么不该回传（一个实用的过滤规则 + 五种明确不报的场景）、格式怎么写（三级信息 + 一句话摘要 + 四个要素）、频率怎么定（事件触发，不是定时触发）。

**亮点设计**

"不是汇报制度，是认知对齐机制"——这句话定义了回传日志的定位。回传不是写日记，是让调度者不需要走进每条线就能安全地做全局判断。一个极简的过滤规则：如果你删掉这条回传，调度者的判断会不会出错？如果不会，就不要写。

## 五个经验包的关系

它们不是独立工具，是一个系统的分层组件：

```
处理流程       → 对应经验包
─────────
开一条新线     → ① 启动规范（怎么开）
运营一条线     → ② 400预警（怎么防丢） + ③ 知识库管理（怎么记）
多条线之间调度  → ④ 决策树（开/停/并/分）
全局状态同步    → ⑤ 回传日志（怎么汇报）
```

最省力的用法：从最痛的环节切入。如果你现在最烦的是"对话截断了什么都丢了"，先接入经验包 2。如果你已经有了多条线、但中枢不知道各线进展，先接入经验包 5。等跑通了，再把其他几个包补上。
